# 瓦片可观测性与大倾角优化方案

日期：2026-09-15。会话类型：决策会话。状态：提交人工评审的实施建议。

事实依据：[瓦片审计报告](../research/tile-overlap-and-pitch-audit-2026-09-15.md)。本文件定义建议范围、次序与候选验收；正式架构和公共 API 的批准状态由人工负责人确定。

行业机制的固定版本来源、内容类型差异与参数适用边界见 [2026-09-16 公开资料核验](../research/industry-tile-streaming-2026-09-16.md)；架构适配评审见 [2026-09-16 方案](2026-09-16-industry-tile-proposal.md)。

## 建议方向

采用四叉树、屏幕误差 LOD、有效可见区域、预测调度、分阶段预算、空间互斥显示覆盖与缓存复用。优先目标为近处细节、完全入雾区域零可见工作、稳态单一地理来源和稳定帧时间。

建议按“真实绘制可观测 → 雾与近处选片 → 覆盖所有权 → 调度与资源分层 → 连续浏览器验收”推进，每一步保留可独立复核的证据。

## 1. 地图上显示实际瓦片编号与层级

建议在面板增加“瓦片调试”开关，默认关闭。开启后提供以下视图：

| 模式 | 地图显示 | 分析目的 |
| --- | --- | --- |
| 实际绘制 | 每个已提交来源的边框、层级色、稳定编号和 `z/x/y` | 观察真正进入 GPU 的瓦片 |
| 目标与来源 | 虚线目标框、实线来源框、连接/高亮关系 | 区分选片粗化与加载回退 |
| 重叠热图 | 同一地面区域来源数 1/2/3+ | 定位父子整片重叠 |
| 指针层栈 | 指针下全部来源，按绘制顺序列出 | 检查被上层遮住的父级、opacity 与用途 |
| 请求与驻留 | 按需显示请求、Worker、上传、GPU/CPU 缓存 | 检查预取及无效工作 |
| 雾与截止线 | 雾开始、完全遮挡、当前加载边界与预测边界 | 对照顶部请求和近处细化 |

标签建议格式：`#42 · z14/13489/6208 · fallback · α1.00`。精确来源标为 `target`，父级覆盖为 `fallback`，有限时过渡为 `incoming/outgoing`。用途可多选，数据状态与绘制角色分别保存。

编号按 source + canonical XYZ + world wrap 在当前会话稳定分配。标签锚点选择实际可见裁剪区域内部，使用碰撞避让；指针与侧栏始终保留完整列表。帧冻结、逐帧/慢放、单层过滤和选中高亮用于检查瞬时交替。隔离某层应同时注明该模式改变了可见内容与性能。

诊断快照建议在渲染提交处生成，包含：`frameId`、时间、实际来源、目标关联、绘制顺序、opacity、transitionId、有效覆盖区域、上传状态、请求原因和各阶段年龄。面板汇总增加 `targetLevels`、`drawnLevels`、`coverageStackDepth`、被完全遮挡的提交数、近处理想/目标/来源差值。覆盖层数与同瓦片面/线 pass 单独显示。

实现建议：Playground 使用单个 Canvas2D overlay 绘制标签与边界，坐标投影跟随相机，文本与列表以低频刷新；SDK 只提供有界只读快照。重叠热图先以地面区域所有权计算，GPU 诊断 pass 作为额外可选模式。调试关闭时跳过标签布局、快照明细序列化和热图 pass。

该快照需要新增或扩展诊断接口；接口定义在进入实现前形成明确批准范围。

## 2. 用有效可见区域分配 LOD

建议先定义完整入雾的地面区域，再开展四叉树细分：

1. 根据 pitch、视口和相机求解屏幕关键射线与地面的交点。
2. 生成前向雾开始/结束平面，与视锥及侧向安全距离形成有限地面区域。
3. 渲染雾和选片共用同一个边界描述；完全位于不透明雾之后的当前视图需求在请求与构建前剔除。
4. 边界相交瓦片保留必要的近侧部分，父级剩余覆盖也受同一有效区域约束。
5. 当前视图、自由运动预测、已知飞行路径各自拥有明确区域和时效。

作为可调的视觉候选，pitch 60° 时可从“顶部 15% 完全入雾，15%–25% 渐变”开始评估；pitch 0°–25° 保持正常俯视范围。具体比例属于待评审视觉参数，来源为用户对顶部雾遮挡的要求，需要实际画面对照确定。边界变化增加迟滞，避免轻微转动造成请求抖动。

LOD 以瓦片在有效区域内的投影尺寸、局部每像素地面尺度、数据层级与纹理分辨率共同计算。近处可以在数据源上限内使用高于视图整数 zoom 的数据层级；建议候选安全上限为 `floor(viewZoom)+2`，具体细化由误差决定。z15 的 512 像素纹理与 z14 的 256 像素纹理需要分别计入采样质量。

预算通过“单位内存/构建成本带来的屏幕质量收益”分配：先满足低雾量、近处、大像素贡献区域，再逐渐降低远处质量。合并使用增加的屏幕误差、受影响面积与字节收益排序，近处质量门槛独立保护。细分/合并阈值分离，邻接差在实际相邻边上计算。

若目标质量超过预算，应在面板明确显示受预算限制的区域。目标集合、实际覆盖与理想质量分别记录，保证验收能发现目标本身过粗。

## 3. 为地面区域定义唯一显示来源

建议将输出从完整来源瓦片集合细化为“覆盖区域 → 当前来源”。父级只负责子级尚未接替的区域。同一个父级资源可被多个剩余区域复用。

建议稳态每个有效地面点由一个数据来源贡献底图；过渡仅在正在接替的区域保留两个来源、同一个过渡编号和明确期限。该约束按数据来源定义，面和道路 pass 保持各自职责。已就绪区域保留内容直到替代来源可用。

| 候选实现 | 优点 | 成本与验证重点 |
| --- | --- | --- |
| 覆盖区域裁剪几何/实例 | CPU 可直接核对所有权；可限制实际几何范围 | 区域碎片和批次数，父级 UV、线条裁剪及 AA 边缘 |
| stencil 所有权遮罩 | 有成熟地图实现参考；可抑制被子级覆盖的父级片元 | 额外遮罩 pass、WebGPU 管线、透明交替和 ID 管理 |
| 片元 owner texture | 可表达复杂区域及调试 ID | 额外纹理读取、遮罩分辨率、更新带宽与边缘误差 |

建议先建立与 GPU 技术独立的空间互斥覆盖描述，随后对“裁剪几何/实例”与“stencil”做同画质、同轨迹对照，依据 GPU 时间、draw calls 与过渡正确性选择。Three.js TSL / NodeMaterial 与 WebGPU 保持当前技术边界。

## 4. 按画面收益调度，分层保留缓存

需求建议划分为有显式语义的优先组：可见缺口 → 近处可见细节 → 其他可见细节 → 近期预测 → 后台预热。同一组按屏幕贡献、误差改善、截止时间、预计剩余成本与等待年龄排序。

基础覆盖的高优先级与真实覆盖缺口绑定；覆盖已满足后，将带宽交给可见细节。即使一次只释放一个槽位，也通过累计配额或 deficit 调度保证可见细节得到进度。下载、Worker 等待、上传分别重排。取消采用需求代际与阶段成本：短请求可完成后进入 CPU 缓存，未开始的过期构建可撤销，执行中的 Worker 结果可留存或丢弃并计量。

自由 pan/zoom/rotate 使用经过限幅的速度与角速度，以及近期网络/构建耗时预测有效区域；与确定的城市路线分开记录。预取范围按运动方向扩展，全方位基础覆盖以少量低成本概览承担。已知目的地保留独立截止时间与工作预算。

缓存建议分开计量编码数据、已解码/已绘制 CPU 数据和 GPU 驻留。当前可见与短期即将显示内容优先进入 GPU；较远的预测保留在 CPU/HTTP 层，临近显示再上传。近期回访使用迟滞和 TTL，长期远离区域按成本与复用收益回收。

流水线内存包含下载 buffer、Worker 输入/输出、待上传 ImageBitmap/实例数组、GPU 纹理及属性。上传按实测时间和字节限额执行，同时保证持续进度；选择计算、上传、覆盖提交各有独立测量。预算数值优先维持当前 256 MiB 约束，按真实计数复核可行性。

## 5. 验收建议

本节为待评审的项目工程标准。最终验收必须同时通过视觉、质量、调度与性能。

| 类别 | 建议断言 |
| --- | --- |
| 来源重叠 | 稳态每个有效地面点来源数为 1；过渡最多 2，退出期限为 140 ms 加最多一帧；重复中断也维持明确上界 |
| 当前有效区 | 完全在不透明雾后的瓦片不产生当前视图请求/构建/提交；相交瓦片、预测与在途任务分别登记 |
| 近处质量 | 北京 z15、60°、2560×1305 下方 1/3 的清晰区域，至少 95% 面积目标数据层级达到 z15；并以源数据上限内理想质量参考验证细节 |
| 通用质量 | 记录理想→目标、目标→来源两类误差，并按清晰近处/中央/远处的屏幕面积分别统计 |
| 连续覆盖 | 运动逐帧有效区域覆盖完整，连续录像检查空白、粗块、边界闪动和过渡接缝 |
| 调度公平 | 一个槽位连续释放时，可见细节得到有界进度；过期工作耗时、字节和占槽时间单独统计 |
| 资源 | CPU/GPU 与流水线均受批准预算约束；条目 ≤384，请求 ≤12，Worker ≤4 |
| 性能 | 保持 P95 ≤18.5 ms、P99 ≤25 ms、>33.34 ms ≤1%、最大帧 <100 ms，并同步检查近处质量 |
| 飞行与回访 | 北京→上海→北京先缩小、平移、放大；到达细节就绪；回访缓存命中、请求及上传增量逐项解释 |

测试矩阵：zoom 10/13/15/17，pitch 0/20/40/60°，多个 bearing，连续滚轮反转、快速 pan 后反向、倾角突变、转向叠加缩放、城市往返、海陆交界与静止收敛。分别记录引擎冷/HTTP 热、HTTP 冷和可控延迟环境。全冷网络的首屏准备时间按实测报告。

性能采样时关闭调试绘制；开启调试时单独记录开销。每次验收输出 frameId 对齐的目标、来源、裁剪区域、队列状态和资源变更，保留录像及关键窗口连续审查。用户人工观感作为最终验收输入。

## 实施边界与产物

建议实施范围为当前 streaming 模块、只读诊断契约、Playground 调试层、相关测试与证据脚本。SDK 保持业务与面板无关，Three.js、TSL、WebGPU 与当前 KYE 数据源继续使用。

首个产物为可查编号、z/x/y、来源栈和雾边界的实际地图调试层；随后通过该工具分别验证选片、覆盖与调度变更。最终产物包含性能报告、逐帧覆盖/质量证据和真实浏览器人工体验记录。
