# Kmap 瓦片调度架构评审方案

日期：2026-09-16。会话类型：决策会话。状态：提交人工评审的建议，架构实施尚待确认。

用户要求以公开论文及成熟地图引擎方案为依据，先给出架构、调整方法与优化顺序。本文件只承载建议；事实与固定版本链接见 [公开资料核验](../research/industry-tile-streaming-2026-09-16.md)，当前 Kmap 实现事实见 [专项审计](../research/tile-overlap-and-pitch-audit-2026-09-15.md)。文中的 M/B/O/C/T/P 编号引用公开资料核验的来源目录。

## 1. 建议采用的路线

以 MapLibre 的平面地图模型为主要参考：视图相关选片、ideal 与 renderable 分离、可用父子回退、瓦片裁剪、source/style 图层绘制与 LRU。Three.js / TSL / WebGPU 负责渲染适配；KYE XYZ MVT、Playground 功能和指标继续作为输入与验收界面。

高倾角采用 MapLibre 局部 LOD 思路，并结合 Mapbox 的可见雾阈值剔除；Cesium 提供部分入雾区域降低地形细节成本的参考。MVT 的质量度量使用地图缩放语义、局部投影采样与源数据层级。下载、Worker 和上传的分阶段处理参考 OpenLayers、Cesium 及 Three.js 生态中的 3DTilesRendererJS。

此路线允许重新划分核心模块。MapLibre 的相关实现依赖自身 transform、source、tile 与 painter，移植范围应明确到固定版本的函数、数据语义和测试；将整套 MapLibre 渲染器作为现成 WebGPU 后端需要另行可行性证据。

## 2. 显示覆盖与必要底图

建议采用“当前目标 + 当前可用显示 + 有限预加载 + 缓存”的模型。

1. 理想目标由相机、数据源和局部 LOD 算出。
2. GPU 可用的目标可直接用于相应区域。
3. 未就绪目标优先复用已有子级覆盖或可用父级；查询复用结果后，再生成必要补充请求。
4. 父子就绪状态和过渡依赖决定本帧有效覆盖。被完全接替且没有过渡用途的父级转为缓存候选。
5. 缓存中可保留多级数据；其显示资格由本帧覆盖计算决定。

平面底图的“父级只覆盖未被子级接替区域”建议作为每个数据源、样式图层的有效贡献语义，依据 M2、M3、O1。实现首选验证 stencil：完整父级资源复用，子级区域通过 stencil 遮罩取得显示范围。需要测量 stencil pass、draw call 与有效片元成本。

例如父级 P 覆盖四个子区域，当前 A/C 已就绪、B/D 尚在加载：A/C 使用子级，P 在 B/D 提供地图内容。P 可保持为同一资源；区域遮罩控制其实际贡献。这里的区域描述无需导出为每帧碎片化几何。

对 Kmap 的面纹理和线实例，建议一个 source 的面/线使用一致的瓦片裁剪归属，并按样式图层管理绘制顺序。普通底色作为地图背景；瓦片数据承担实际地图内容。缓存父级能够维持已有区域的显示，但全冷的新区域仍有真实数据准备时间。若需要更强的全冷首帧保障，可评估预置概览数据，单独核算覆盖范围、版本、体积与质量。

## 3. 渲染方式的适配选择

| 内容 | 建议 | 来源和验证重点 |
| --- | --- | --- |
| 当前面纹理 | 先验证 raster 方式的目标/父纹理 UV 映射、单区域双采样与裁剪 | M3；测纹理采样、颜色、透明度、上传、AA 与明显粗块 |
| 当前矢量道路实例 | 使用矢量 clipping mask，线宽按当前视图样式计算；来源替换以就绪状态为依据 | M2；验证接缝、圆端点、道路连续性和重复加深 |
| 原生矢量 fill + line | 作为同数据、同样式、同轨迹的对照实现，采用 Worker 构建和按图层批处理 | MapLibre 矢量路径；测构建/上传成本、内存及放大清晰度 |
| symbol / 业务图层 | 维持各自的碰撞、生命周期与透明度语义 | 和瓦片来源切换分别计量 |

建议第一轮用当前面纹理与线实例验证覆盖和调度，建立最小 WebGPU 纵向样例；并用代表性瓦片评估原生矢量 fill 的成本。最终数据表达选择由对照实验确定。面纹理具有可控网格数量和纹理带宽成本；原生矢量具有放大质量优势及几何构建、上传成本。

父子跨层淡变按内容类型定义。栅格支持局部单次绘制双纹理过渡；道路来源切换、样式插值和标签淡变分别管理。具体时长属于产品参数，验证覆盖完整、道路连续和快速反转时的状态收敛。

## 4. 高倾角的选片方法

建议 `ViewCoverage` 与 `FogPolicy` 输出可测试的当前视图参数，供选择、请求和渲染使用：

1. 根据当前投影、相机/FOV、视口、bearing 和 pitch 构造视锥；平面地面与有高度的内容分别使用适合的包围体。
2. 使用明确的雾函数计算衰减和可剔除阈值。对包围体完全处于阈值后的区域，在请求和细分前剔除；跨边界瓦片按其仍可见部分保留。
3. 对可见候选计算局部所需数据层级，采用 M4 的距离、倾角和瓦片数量控制思路，核对 Kmap 256 CSS 像素语义与 MapLibre 的 tileSize 换算。
4. 分开保存 camera zoom、canonical data zoom、overscaled/style zoom 和 raster texture resolution。数据源最大层级约束数据请求；放大采样和样式继续依据实际视图。
5. 半透明雾区允许较低细节；近处清晰区域按局部投影质量细化。质量不足时记录受预算限制的区域及原因。
6. 相机变化重新计算有效范围；进入/退出边界的缓存迟滞独立于当前可见请求，避免转动和倾角抖动造成持续重载。

雾的位置由透视关系和视觉设置决定。屏幕顶部遮挡比例作为调试结果显示。若产品要求顶部一定范围完全遮挡，可用该视觉目标反求雾参数，再以相同参数验证裁剪。

Mapbox 的约 98% 不透明度阈值和 Cesium 的全雾剔除均有来源。Kmap 建议先验证与其背景连续的完全遮挡边界，再根据视觉对照评估容差。未来增加立体建筑或地形时，包围体与越过雾/地平线的内容保留必须一并适配。

## 5. 调度、预加载与缓存

建议每个需求携带 `reason`、当前视图代际、预计使用时间及可见影响。一个瓦片可同时满足多个需求，取消由剩余需求决定。

| 阶段 | 建议职责 | 依据 |
| --- | --- | --- |
| 需求生成 | 当前理想细节、真实覆盖缺口、已有替代资源、预测视图分别记录 | M1、O1 |
| 网络准入 | 去重、当前可见优先、有界并发；返回视图更新后的有效优先级 | O1、T1 |
| Worker | 使用独立可重排等待队列；未开始的过期构建移出队列，执行中结果检查代际和缓存价值 | T1 的解析队列/取消；Worker 细则为 Kmap 适配 |
| GPU 上传 | 当前覆盖与可见细节优先，字节和帧时间约束；到达 CPU-ready 即进入可调度状态 | C1 时间切片参考；上传细则为 Kmap 适配 |
| 显示提交 | 本帧可用资源和裁剪状态一致提交；提交完成后处理过渡与依赖释放 | M2、M3 的渲染语义 |
| 回收 | 可见与替代依赖保护；离开视图的数据按复用价值进入 LRU、最终确定性销毁 | M1、C1、T1 |

请求排序建议先区分真实缺口、可见细节和预测需求，再用屏幕影响、距焦点距离与等待时间排序。对于当前已有可用地图的区域，精细目标持续获得进度。具体公平机制和配额通过单槽、慢网、反向运动实验确定。

预加载建议覆盖三类明确用途：短期相机运动、低成本缩小层级、已知城市飞行。自由手势的预测提前量应由真实网络/构建耗时与运动速度约束。已知飞行路径的 next views 可提前准备，远期数据优先留在 CPU/HTTP 层，临近使用时才占 GPU。

当前完全入雾且没有近期显示用途的远处瓦片从需求集合剔除。跨雾边界的瓦片、飞行下一视图的瓦片分别显示原因和成本，预取也受边界和配额约束。

缓存建议独立记录编码数据、Worker 产物和 GPU 资源。驻留预算纳入在途 buffer、待上传 ImageBitmap、实例数组及 GPU 资源；主线程禁止同帧集中上传大量就绪瓦片。LRU 回收不直接改变理想 LOD；质量降级单独记录。

## 6. 建议模块与契约

```text
相机 + 数据源 + 雾设置
  → ViewCoverage：可见性与局部理想层级
  → TileDemand：当前 / 回退 / 预测需求
  → TileStore：编码、CPU-ready、GPU-ready、引用与字节
  → FetchQueue → WorkerQueue → UploadQueue
  → RenderCover：本帧来源、区域归属、过渡依赖
  → WebGpuTileRenderer：遮罩、面/线、纹理与雾
  → Diagnostics：本帧真实提交及队列时序
```

建议将 `engine.ts` 的需求、生命周期、显示覆盖和回收拆为上述职责，单个协调入口只推进流程。关键契约包括完整 source/revision/canonical/wrap 身份、数据状态、需求原因与期限、有效显示区域和资源引用。样式修改对构建缓存的失效关系单独定义。

有效空瓦片、服务不存在、网络失败和加载中分别处理。空数据是否允许继续显示祖先中的要素由数据源语义决定；需用 KYE 204 的实际含义验证，避免空区域永远被祖先内容填充。

当前审计事实与建议调整的对应关系：

| 当前已核验事实 | 建议调整 | 验证输出 |
| --- | --- | --- |
| `resolveCover` 聚合完整父子 surface；CPU 样例有三层 opacity 1 的提交来源 | 将可用资源集合和有效区域归属分离，使用渲染遮罩限制重复贡献 | 实际 draw 来源、stencil/区域归属及 GPU 成本 |
| 局部目标受 `floor(view.zoom)` 上限及约 80 叶片合并影响；pitch 60° 样例仅 3 张 z15 | 按 M4 适配局部层级与数量控制；质量受限区域单独输出 | 不同 pitch/FOV/视口的 near/mid/far 目标和来源质量 |
| 该视图当前目标 79 个、其他准入需求 143 个，首批 8 个祖先与 4 个目标 | 从覆盖缺口和当前细节生成有限需求，预测拥有独立时效与成本 | 无效工作、可见细节排队时间和首次清晰时间 |
| 当前中心截止圆在 pitch 60° 样例只产生约 2.9% 完全入雾地面采样 | 明确视觉雾目标与剔除条件，先剔除完全遮挡区域再分配细节 | 雾函数、剔除边界、请求区域对齐图 |
| Worker 等待为 FIFO，过期构建在后续上传阶段检查；就绪状态与 GPU 驻留耦合 | Worker 等待重排/取消，CPU-ready 与 GPU-ready 分离 | 各阶段年龄、取消、缓存复用、上传字节与帧时间 |

这些数字来自专项审计的指定视图或探针。实际浏览器中的发生频率、成本和修复收益由集成实验测量。

## 7. 实施次序与评审产物

| 次序 | 范围 | 可评审产物 |
| --- | --- | --- |
| 1 | 实际渲染诊断和固定版本参考样例 | z/x/y、canonical/overscaled、用途、有效区域、提交/贡献层数、请求原因、雾边界；代表性场景基线 |
| 2 | Three.js WebGPU 覆盖纵向样例 | z13 父级与部分 z14 子级，面/线裁剪、栅格过渡、透明度、AA、快速反转；原生矢量 fill 对照成本 |
| 3 | ViewCoverage 与 FogPolicy | 视角矩阵目标集及投影质量图；与固定 MapLibre 参考函数结果对照并解释差异 |
| 4 | TileDemand、分阶段队列与 TileStore | 慢网、乱序、单槽、取消、重复请求、缓存回访与内存压力证据 |
| 5 | 连续 WebGPU 集成验收 | 首屏、pan/zoom/rotate/pitch、城市往返的录像、逐帧来源/质量/帧时间与人工观感 |

参考样例应使用同一 KYE 数据、相机投影和样式语义；算法结果可离线作对照。最终应用仍以 `http://127.0.0.1:5173/` 的真实 WebGPU 浏览器运行验证。网络缓存、分辨率、DPR、硬件与实际服务端口随证据记录。

## 8. 建议验收方式

这里定义项目验收建议。来源支持机制，性能数字取自项目当前验收文件或后续实测配置。

| 维度 | 建议判据 |
| --- | --- |
| 覆盖 | 已有可用数据的显示区域在替换时连续；新暴露/全冷区域分别记录无数据持续时间与首次可用画面时间 |
| 来源归属 | 对同一 source/样式图层，稳态父级在子级接替区域无重复内容贡献；过渡参与者、权重、依赖与退出可解释 |
| 质量 | 记录 ideal→budgeted target→rendered source 三段差异，清晰近处/中景/雾区按屏幕面积分开统计；与同样式参考画面核对 |
| 雾边界 | 当前视图完全遮挡区域无独立可见细节需求；边界相交与未来视图需求分别计量，转动/倾角变化无切边闪现 |
| 调度 | 可见细节持续推进；每个等待项有原因/年龄，过期下载、构建、上传及无效字节可量化 |
| 资源 | 当前 CPU/GPU 各 256 MiB、条目 384、网络 12、Worker 4 作为现有对照配置；流水线内存加入统计 |
| 帧时间 | 当前项目门槛 P95≤18.5 ms、P99≤25 ms、>33.34 ms≤1%、最大帧<100 ms 作为基础门槛；按目标刷新率再分析错过呈现机会及连续卡顿 |
| 联合验收 | 视觉质量和帧率在同一轨迹同一次记录中通过；调试渲染开销独立采样 |

性能门槛是 Kmap 工程门槛。60 Hz 的单帧时间预算约 16.67 ms，实际稳定性同时取决于连续帧时间、GPU 完成和呈现。仅满足分位数不足以证明体验稳定。

测试矩阵覆盖 zoom 10/13/15/17、pitch 0/20/40/60° 及产品允许的最大倾角、多个 bearing、连续滚轮反转、拖动反转、旋转叠加缩放、倾角突变、海陆边界、北京→上海→北京和静止收敛。包含引擎冷/HTTP 热、HTTP 冷和受控延迟环境。

连续检测建议：每帧轻量状态日志与 frameId、浏览器录像、关键窗口逐帧检查、来源归属诊断图与队列时间线对齐。检查白块、突发粗块、道路粗细变化、重复加深、边界闪动、细节迟到和城市到达清晰度。录像丢帧单独计量；必要时补充 GPU/呈现跟踪。浏览器采集证据与人工实际观感共同作为验收输入。
